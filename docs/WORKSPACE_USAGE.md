# Slack 작업 요청 가이드

**`[폴더명]`으로 기존 작업 폴더를 선택하고, `[새 프로젝트: 폴더명]`으로 새 폴더에서 시작할 작업을 요청해요.** Git 저장소와 일반 폴더에 같은 규칙을 사용해요. 연결이 아직 안 되어 있다면 [설치·연결 가이드](DOT_SLACK_SETUP.md)부터 진행하세요.

## 매번 이렇게 보내세요

**대상 폴더 + Workspace Gateway 사용 + 할 일과 완료 범위**를 한 메시지에 적어요. 긴 공통 지침을 먼저 보내거나 영구 저장할 필요는 없어요. 채널에서는 연결한 실제 dot을 멘션하고, 같은 작업의 후속 요청은 해당 스레드에 보내요. DM에서는 멘션을 생략할 수 있어요. 아래 `@dot`은 설명용 표기예요.

### 조사만 요청하기

```text
@dot [ch-dropwizard] Workspace Gateway로 ○○ 오류의 원인을 조사해주세요.
관련 코드와 근거를 알려주시고, 파일은 변경하지 마세요.
```

### 수정과 테스트 요청하기

```text
@dot [ch-dropwizard] Workspace Gateway로 ○○를 리팩토링하고 관련 테스트를 실행해주세요.
기존 변경은 보존하고, 다른 진행 중인 작업은 중지하거나 취소하지 마세요.
변경 파일, 실제 테스트 출력·종료 코드와 남은 문제를 이 스레드에 알려주세요.
```

### worktree부터 PR까지 요청하기

```text
@dot [cht-open-api] Workspace Gateway로 ○○ 기능을 추가해주세요.
upstream/exp를 기준으로 별도 worktree에서 작업하고 관련 테스트를 실행해주세요.
변경을 커밋하고 origin에 푸시한 뒤 upstream의 exp 대상으로 Draft PR을 만들어주세요.
기존 변경과 다른 진행 중인 작업은 그대로 두세요.
실제 worktree 경로, 검증 결과와 PR 링크를 이 스레드에 알려주세요.
```

`upstream`·`origin`과 `exp`는 예시예요. 저장소의 실제 원격·기준 브랜치에 맞춰 바꾸세요. PR까지 원하지 않으면 수정·테스트 예시를 사용해요. GitHub 작업은 호스트의 Git/`gh` 인증이 필요하고, worktree 생성은 해당 프로젝트의 도구·지침을 따라요.

새 폴더는 아래 [새 폴더 예시](#2-새-폴더에서-시작하기)를 사용해요. AI가 해야 하는 대상 확인·프로젝트 지침 읽기·도구 결과 검증은 서버의 MCP 지침으로 제공돼요. 사용자는 매번 그 내부 절차를 길게 적을 필요가 없어요.

## 이름은 무엇을 뜻하나요?

예를 들어 공유한 부모 폴더가 다음과 같다고 가정해요.

```text
~/desktop/project/             ← 공유 부모 폴더
├── ch-dropwizard/             ← Git 저장소인 작업 폴더
└── calculator-demo/           ← Git 저장소가 아니어도 되는 작업 폴더
```

| 용어 | 의미 |
|---|---|
| 공유 부모 폴더 | 관리 화면에 공유 등록한 경로. 예: `~/desktop/project` |
| 작업 폴더 | 그 부모 바로 아래에서 작업할 실제 폴더. 예: `ch-dropwizard`, `calculator-demo` |
| Git 저장소 | Git으로 관리하는 작업 폴더. 이름 선택 기능은 Git 여부를 검사하지 않아요 |
| 관리 화면의 Projects 이름 | 공유 경로에 붙이는 표시 이름. 예: `Coding Projects`. 요청에 쓰는 폴더명과 달라요 |
| ChatCmd 작업 (`taskId`) | 도구 호출과 실행 기록을 묶는 단위. 폴더명이나 Slack 스레드와 같은 개념이 아니에요 |

**`[ch-dropwizard]`를 쓴다고 저장소가 별도의 프로젝트로 변환되거나 등록되지는 않아요.** 공유 부모 아래 `ch-dropwizard` 폴더를 선택할 뿐이에요. `[calculator-demo]`도 똑같이 그 이름의 실제 폴더를 선택해요. 프로젝트 제목, Git 원격 저장소 이름, 임의 별칭 대신 **실제 폴더명**을 쓰세요.

## 1. 기존 폴더에서 작업하기

```text
@dot [ch-dropwizard] Workspace Gateway로 이 버그의 원인을 조사하고 관련 코드와 테스트를 알려주세요.
```

공유 부모 바로 아래에 `ch-dropwizard` 폴더가 존재해야 해요. 하위 경로나 절대 경로를 태그에 넣지 않아요. 자신의 실제 폴더명으로 바꾸고, Gateway 호스트 작업임을 알 수 있게 Workspace Gateway 사용을 명시해요.

## 2. 새 폴더에서 시작하기

```text
@dot [새 프로젝트: calculator-demo] Workspace Gateway로 Python 계산기와 unittest를 만들고 실행해주세요.
기존 파일을 확인하고 다른 폴더는 변경하지 마세요.
다른 진행 중인 작업은 중지하거나 취소하지 마세요.
실제 출력과 종료 코드를 확인해주세요.
```

이 태그는 **새 작업 폴더를 만들 의도와 이름**을 전달해요. ChatCmd는 공유 부모를 선택하고, dot이 그 아래 `calculator-demo` 폴더와 파일을 도구로 생성해요. 태그 자체가 폴더를 만들거나 `git init`, GitHub 저장소 생성, 관리 화면의 Projects 등록을 실행하지는 않아요.

새 폴더 이름은 아직 존재하지 않는 이름을 사용해요. 이미 있다면 새 프로젝트 태그로 덮어쓰기를 요청하지 말고 `[calculator-demo]`로 기존 내용을 확인하세요. 공유 부모는 하나여야 해요.

## 3. 만든 폴더에서 이어서 작업하기

**폴더 생성이 완료되었다면 다음 요청부터는 `[calculator-demo]`를 사용해요.** 기존 Git 저장소를 선택할 때와 같은 방식이에요.

```text
@dot [새 프로젝트: calculator-demo] Workspace Gateway로 계산기와 테스트를 만들고 실행해주세요.
```

dot이 실제 폴더·파일 생성과 실행 결과를 확인한 뒤, 다음 요청을 보내요.

```text
@dot [calculator-demo] Workspace Gateway로 나머지 연산을 추가하고 테스트를 실행해주세요.
```

그다음에도 같은 폴더 이름을 붙여요.

```text
@dot [calculator-demo] Workspace Gateway로 방금 변경한 파일과 테스트 결과를 확인해주세요.
```

새 프로젝트 태그는 생성 요청에 사용하고, 이후 요청은 기존 폴더 태그로 통일해요. 생성 실패로 폴더가 없다면 기존 폴더 선택도 수락되지 않아요. dot이 실제 생성 여부를 확인한 뒤 이어서 진행해야 해요.

## Slack 스레드와 작업 폴더

Slack 스레드는 요청·답변을 정리하는 단위이고, 폴더 태그는 작업 대상을 선택해요. 태그가 독립 작업 ID를 만들지는 않아요. 2026-10-03 실제 검증에서는 두 스레드가 같은 ChatCmd `taskId`를 받았지만, dot 내부 대화 상태가 같은지는 확인하지 못했어요. **같은 ID라는 이유로 다른 프로젝트나 실행 중인 작업을 중지하지 마세요.**

여러 요청을 진행할 때도 다음 원칙을 사용해요.

1. 후속 요청을 포함해 매 요청에 `[폴더명]`을 붙여요.
2. dot은 각 실행의 작업 디렉터리 `cwd`와 파일 대상을 명시적으로 확인해요. Git 변경을 분리할 때는 별도 worktree를 사용해요.
3. 실제 대상 충돌이 확인되면 **이번 요청의 변경 작업만** 보류하고 상황을 알려요. 다른 작업을 중지하거나 취소하지 않아요. 스레드 자체가 접근 격리를 보장한다고 해석하지 않아요.

태그 없는 요청은 서버의 마지막 수락 선택을 유지하지만, 다른 스레드의 선택이 그 값을 바꿀 수 있어요. 따라서 "계속해주세요"만 보내는 방식에 의존하지 않아요. [검증 결과와 제한](GATEWAY_OPERATIONS.md#실제-검증-결과)에 성공·실패 범위를 기록했어요.

## 선택이 안 되는 경우

| 요청·상태 | 처리 |
|---|---|
| `[없는폴더]` 또는 이름 오타 | 새 선택을 수락하지 않아요. 이전 선택이 남을 수 있으므로 쓰기·실행 전에 실제 폴더를 확인해요 |
| 같은 이름이 여러 공유 부모 아래 존재 | `project_selector_ambiguous`. 관리 화면에서 작업에 프로젝트 경로를 명시하는 등 대상을 분명히 정해요 |
| 새 프로젝트 요청인데 공유 부모가 여러 개 | 부모가 모호해요. 사용할 공유 부모 설정을 확인해요 |
| `[이름](URL)` 또는 `[부모/하위]` | 폴더 선택 태그가 아니에요 |
| 작업에 이미 명시적으로 연결된 프로젝트 경로가 있음 | 해당 경로가 이름 태그보다 우선해요. 실제 적용 폴더를 확인해요 |

태그는 요청 맨 앞에 쓰고 닫는 `]` 뒤에 공백을 넣어요. 선행 dot 멘션 하나는 허용해요. 공유 범위 밖으로 향하는 심볼릭 링크는 선택할 수 없어요. 폴더명이 수락되지 않았으면 dot이 이번 요청의 쓰기·실행을 보류하고 대상을 확인해야 해요.

## AI가 대상을 확인하는 방식

이 내용은 사용자가 매번 붙여 넣는 템플릿이 아니라 설치·진단을 위한 설명이에요. 서버는 이름 태그가 있는 현재 요청 원문을 `agent_user_message`로 한 번 기록하고, 반환된 `sharedProjectSelection`과 실제 `projectFolder`를 사용하도록 AI에게 안내해요. `workspace_roots`·`workspace_context`로 경로·지침을 확인하고 관련 스킬을 읽도록 하는 지침도 포함해요. 미수락·모호한 선택이면 이전 작업 폴더에 쓰지 않아요. 전체 규약은 [MCP 도구 문서](mcp_method.md#shared-project-selection)를 참고하세요.

이 지침이 모델의 행동을 강제로 보장하지는 않아요. 연결 검증에서는 실제 호출·선택·출력·종료 코드를 대조해요. 권한은 프롬프트 저장과 별개이며 [설치·연결 가이드](DOT_SLACK_SETUP.md#3-읽기쓰기명령-실행-권한-설정)에서 설정해요.

호스트의 다른 CLI는 설치·인증·도구 권한이 있으면 명령 실행으로 사용할 수 있어요. Codex의 MCP 목록·세션·서브에이전트 하네스가 자동으로 중계되지는 않아요. 필요한 외부 서비스는 dot의 지원 플러그인으로 따로 연결하거나 허용된 호스트 CLI를 사용해요. worktree가 공유 부모 밖에 있다면 실제 경로의 접근 승인을 먼저 확인해요. 거절이 나면 해당 요청의 경로 권한을 해결하고 이어서 진행해요.

## 도구 경로를 이해해야 할 때

일반 요청에서는 위 두 태그만 사용하면 돼요. 직접 도구 호출을 점검할 때는 다음 차이를 확인해요.

| 수락된 요청 | `@project` 기준 | 파일·실행 경로 예시 |
|---|---|---|
| `[새 프로젝트: calculator-demo]` | 공유 부모. 폴더가 생성된 뒤에도 같은 요청의 기준은 부모로 유지 | `@project/calculator-demo/calculator.py`, 실행 디렉터리 `@project/calculator-demo` |
| 이후 `[calculator-demo]` | 생성된 `calculator-demo` 폴더 | `@project/calculator.py`, 실행 디렉터리 `@project` |

이 표는 명시적으로 연결된 작업 프로젝트 경로가 없는 경우예요. 실제 도구 응답과 [MCP 선택 규약](mcp_method.md#shared-project-selection)이 기준이에요. 공유 해제 후 파일·터미널 세션 접근은 권한을 다시 확인하며, 공유 설정이 이미 실행한 프로그램의 OS 접근을 격리하거나 되돌리는 것은 아니에요.
